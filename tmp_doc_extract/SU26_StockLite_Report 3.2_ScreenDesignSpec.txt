Purpose & Scope
This document defines the design language, information architecture, navigation access, screen flows, and screen-level layout specifications for the StockLite project.
It covers the Angular Web Admin dashboard and Flutter Mobile warehouse workflow, including visual foundations, Site Map, main user flows, screen states, layout zones, and mockup references.
The approved Figma design file is the visual source of truth for all pixel-level decisions, including spacing, alignment, component placement, and screen appearance.
Part 1 — Design Language
1.1 Design Principles
#
Principle
What It Means in Practice
1
Speed for warehouse operations
Receiving, picking, and counting screens prioritize scan-first actions and reduce unnecessary confirmation steps.
2
Status always visible
Every operational screen shows the current document status, scan result, discrepancy state, and next action.
3
Errors prevent wrong stock movement
The UI blocks invalid QR, missing quantity, unresolved weight discrepancy, and unauthorized confirmation before stock changes occur.
4
Manager control without complexity
Warnings and suggestions explain the reason and allow documented override instead of hiding business logic.
5
Consistent cross-device workflow
Angular web admin manages setup and supervision; Flutter mobile executes fast warehouse tasks with the same terminology.

2.3 Navigation Patterns
Attribute
Angular Web Admin Specification
Pattern
The Angular Web Admin uses a fixed left sidebar and a sticky top bar for authenticated pages. 
Sidebar width 
The desktop sidebar uses a fixed width of 260px. 
Sidebar content 
The sidebar contains the application logo, dynamic navigation menu, expandable parent-child menu groups, and a user information card at the bottom. 
Dynamic menu loading 
Navigation items are loaded from the menu service. If menu loading from the server fails, the layout falls back to the authenticated user's cached menu data. 
Nested navigation 
Parent menu items can be expanded or collapsed. Child menu items are displayed under the parent menu with indentation and dot indicators. 
Top bar 
The top bar contains a mobile menu button, application brand text, global search input, notification button, and user menu.

Part 5 — Responsive & Accessibility Rules
5.1 — Navigation 

Breakpoint
Angular Web Admin Behaviour
Desktop (>= 1025px)
Use a fixed left sidebar of approximately 260px and a sticky top bar. Menu icons, labels, nested groups, notification button, global search, and user menu are visible. Main content uses the remaining width with a maximum content width on wide screens.
Tablet (768-1024px)
Use compact navigation. The sidebar may collapse to icon-only or become a drawer depending on available width. The top bar remains sticky; search can shrink into an icon/button if space is limited. Nested menus keep the same permission-based visibility.
Mobile (< 768px)
Hide the desktop sidebar. A hamburger button opens an overlay drawer. The top bar should show only the menu button, page title or brand, notification action, and user menu. Avoid placing full admin tables as the main mobile pattern.
5.2 Content Layout

Breakpoint
Layout Behaviour
Examples in StockLite
Desktop
Use 12-column layouts, multi-column card grids, full-width data tables, side-by-side filters, and modal forms where appropriate. Dashboard and report screens can use 2-3 column KPI/card groups.
Dashboard KPI cards; Products & SKUs tables; Inbound / Outbound document lists; Reports & Analytics charts; Users and Warehouse management.
Tablet
Use 8-column layouts. Reduce dense grids to two columns. Move long filter sets into two-row toolbars or collapsible filter panels. Preserve important status badges and action buttons.
Inventory monitoring, Alerts, Product search/filter panels, Stocktake overview, and IoT status cards.
Mobile web
Use a single-column layout. Full-width form fields, stacked cards, compact headings, and sticky primary actions. Avoid exposing dense admin-only tables unless horizontal scrolling is explicitly selected.
Operational summaries, simple lookup/detail pages, and notification/profile screens.
Flutter Mobile
Use task-first single-column screens. Prioritize the current document, scan result, quantity/weight input, discrepancy status, and next action. Secondary data is moved to expandable details or a separate detail page.

5.6 Mobile Operational Workflow Rules
Rule
Specification
Scan-first layout
Mobile receiving, picking, packing, and stocktake screens must place QR scanning or scan results near the top of the workflow. The next required action must be visually obvious.
Weight and quantity visibility
Received quantity, picked quantity, IoT weight, tolerance status, and discrepancy state must remain visible before confirmation.
Bottom safe-area action
Primary operational buttons such as Scan, Confirm Receiving, Confirm Pick, Confirm Pack, Submit Count, and Retry Validation should be placed near the bottom safe area and remain reachable with one hand.
Offline or weak network
Show connection status and retry options for server validation. Do not silently discard scan, weight, or count input.
Task card priority
Mobile task cards show code, status, priority/date, assigned warehouse or location, progress, and the next action. Detailed metadata moves to a detailed view.
5.7 Accessibility-Related Responsive Rules 
Rule
Specification
Reason
Touch targets
All mobile interactive elements must use at least 44 x 44 px touch targets. Scan and confirm controls should be at least 48px high.
Prevents missed taps during warehouse work and supports gloved or one-handed use.
Status badges
Document, stock, alert, and discrepancy status must use both colour and text. Icons may support the state but cannot be the only signal.
Users must understand status even if colour perception or screen conditions are limited.
Error visibility
Validation errors appear inline near the field and may also appear as a toast for action-level failure. The system must not clear user input on validation failure.
Users can correct the exact problem without repeating warehouse input.
Loading states
Data loading uses skeletons or spinners. Blocking actions disable the action button and show progress until the server responds.
Prevents duplicate submissions and accidental stock movement.
Focus and keyboard support
Web admin screens keep logical focus order when columns collapse, filters move to a drawer, or dialogs become full-screen.
Responsive layout must not break keyboard navigation or form completion.
Readable codes and numbers
SKU codes, document codes, quantity values, weight readings, and location codes must not be truncated without a tooltip/detail option.
Warehouse decisions depend on exact identifiers and quantities.
