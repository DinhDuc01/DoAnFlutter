Part 0 — Document Overview
This Software Requirements Specification defines StockLite requirements for Report 3. It translates the approved Vision & Scope and Project Plan baseline into system scenarios, activity diagrams, feature behaviour, data requirements, acceptance criteria, business rules, non-functional requirements and RTW traceability. The RTW workbook is the control artifact used to map features, use cases, scenarios, permissions, data entities, business rules, NFRs and tests.
The document is limited to the MVP scope: one active warehouse per business account, Angular Web Admin, Flutter warehouse mobile app, .NET 8 Web API, QR-based warehouse execution, ESP32 scale verification, SignalR realtime updates, and rule-based decision support. Marketplace synchronization, accounting, payment, courier API integration, advanced AI/ML optimization, multi-warehouse transfer and financial return handling are outside MVP scope.
Part 1 — System Overview
1.1 System Objective & Business Context
StockLite is a lightweight warehouse management system for Vietnamese SME e-commerce sellers. It replaces spreadsheet/chat/paper tracking with controlled inbound, outbound, stocktake, returns, QR scanning, IoT weight verification, inventory transaction logging, reporting, low-stock alerts, bottleneck warnings and put-away suggestions.

Figure 1. System Context Diagram — StockLite MVP Boundary
StockLite is a centralized smart warehouse management system (WMS) designed to digitalize, automate, and optimize the internal logistics and operational workflows of modern warehouses. This system replaces fragmented, manual inventory tracking with an integrated digital interface for managing multi-tier warehouse configurations, automated stocktakes, task assignments, and real-time operations. To optimize interactions and bridge the gap between digital management and physical operations, the system seamlessly integrates with third-party automation hardware and services. This includes IoT Scale Devices for automated weight-based validation, QR Printers for instant product/variant physical labeling, and an external Notification Service to dispatch real-time operational alerts and system notifications. The primary goal of StockLite is to provide an optimal management environment where warehouse managers can effectively plan capacity, monitor performance, and mitigate bottlenecks, while warehouse staff benefit from clear, automated step-by-step operational guidance.
Interaction with External Entities:
Warehouse Manager: Authenticated administrative users who hold high-level control over warehouse operations. They review system-generated inventory reports, handle pending approvals, analyze operational bottlenecks, assign staff to specific duties, and utilize analytics for warehouse capacity planning.
Warehouse Staff: On-the-ground operational users who execute day-to-day warehouse tasks. They receive clear system instructions for material handling and supply feedback to the system by submitting real-time execution data such as picking, receiving, and physical stocktaking.
System Admin: System administrators responsible for the platform's baseline configuration. They handle user provisioning, set up initial warehouse layouts, define operational system rules, and monitor system health via audit logs.
IoT Scale Devices: External hardware components integrated into the warehouse infrastructure. They constantly feedback physical measurement data to the system and respond to remote operational commands or calibration protocols initiated by StockLite.
QR Printer: External hardware peripherals utilized for physical labeling. The system triggers print jobs directly to these devices to generate tracking stickers for inventory tracking, while the printers report back job execution status or hardware errors.
Notification Service: A third-party communication gateway or service infrastructure responsible for routing automated alerts (via Email, SMS, or Push notifications) to relevant stakeholders based on triggers set within StockLite.

 Table 9: SC-03 Scenario Details - Receive inbound goods with QR and IoT verification
Narrative: After approval, staff open the mobile receiving task and scan the QR/SKU for each line. Staff record the received quantity (which may differ from the ordered quantity) and may split a received line into multiple receiving groups for checking, weighing and quality handling. For each group, staff attach stable IoT weight evidence; the system compares expected weight (unit weight × quantity) against actual weight. Verified quantities are held pending put-away and final confirmation in SC-04.

Figure 5. Activity Diagram - SC-03 Receive inbound goods with QR and IoT verification

System Response / Outcome

Weight outside tolerance
Flag discrepancy and require manager review before confirmation.
Short / over / damaged / failed-QC
Record a discrepancy reason and route the affected quantity to a quarantine (non-available) location instead of available stock.

 Table 11: SC-04 Scenario Details - Store received goods using put-away suggestion
Narrative: During receiving and before final confirmation, the system recommends a suitable location for each verified receiving group using category compatibility, available capacity, current occupancy and priority. Staff accept the suggestion or override it with a reason. After locations are assigned, staff perform the single final receiving confirmation: inventory is increased at each confirmed location, receiving groups are aggregated into inventory balances by ProductVariant and Location, and an inbound InventoryTransaction plus audit record are created.

4.2 State Transitions
Entity / Process
Allowed States
Important Rules
Inbound Document
Draft → Submitted → Approved / Rejected → Receiving → Partially Received / Fully Received → Confirmed / Cancelled
Inventory increases only after final receiving confirmation. Put-away location must be assigned during receiving before the document reaches Confirmed state.
Outbound Document
Draft → Submitted → Approved / Rejected → Reserved → Picking → Packed → Shipped / Cancelled
Reserved quantity must not cause available inventory to become negative. Inventory decreases only after shipment or dispatch confirmation.
Customer Return Order (CustomerReturnOrderStatus)
Draft → Submitted → Pending Inspection → Pending Approval → Approved → Closed. Rejections may occur from Submitted, Pending Inspection, or Pending Approval.
Inspection is performed against CustomerReturnOrderItem; no separate ReturnInspection entity is used. QR validation is required unless an authorized manual verification is recorded. Good quantity requires an active non-quarantine restock location. Damaged quantity requires an active quarantine location and damage reason. Inventory changes only after final approval.
Return-to-Supplier Order (ReturnToSupplierOrderStatus)
Draft → Submitted → Approved → Picking → Dispatched → Closed. Rejected may occur before approval; Cancelled may occur before dispatch.
Return-to-Supplier does not use the Customer Return inspection lifecycle. Approval authorizes picking but does not change inventory. Inventory decreases only after confirmed dispatch with valid actual returned quantities.
Stocktake Session
Draft → Counting → Submitted → Manager Review → Approved Adjustment / Rejected → Closed
Inventory adjustment requires manager approval and an approval or rejection reason. Stocktake variance equals ActualQuantity - SystemQuantity.
Low Stock Alert (Alert)
Active → Acknowledged → Resolved
A Low Stock alert is created when available quantity is at or below the configured threshold. Only one active Low Stock alert may exist for the same Warehouse and ProductVariant. The alert is resolved when stock recovers above the threshold or an authorized manager closes it.
Inbound Bottleneck Alert (Alert)
Active Warning / Active Critical → Acknowledged → Resolved
Normal, Warning, and Critical are evaluation results. Only Warning or Critical requires an active Alert record; Normal resolves the existing active bottleneck alert. The warning is advisory only and must not cancel, block, reserve, or modify inbound documents.
IoT Device
Registered → Online ↔ Offline → Maintenance / Disabled
Device online status is derived from the latest valid heartbeat. A device without a valid heartbeat within the configured timeout becomes Offline. Offline or Disabled devices cannot receive TARE, RESET, or CALIBRATE commands.
IoT Device Command
Pending → Picked Up → Executed / Failed / Expired
Only Pending commands may be picked up or expired. A command is marked Expired when ExpiredAt is reached without a valid completion result. Executed, Failed, and Expired are terminal states.
Notification Delivery (FcmNotificationLog)
Created / Unsent → Sent. Unsent → Retry Eligible → Sent / Soft-Deleted
The same notification-log record is retried; a new log must not be inserted for the same delivery attempt. Successful delivery sets IsSent = true. Permanent failures set IsDeleted = true. The current schema does not store RetryCount or NextRetryAt.
User Session (UserSession)
Active → Revoked / Expired
Expired sessions are invalidated by setting IsRevoked = true. Valid unexpired sessions must remain usable.
User Verification Token (UserVerificationToken)
Valid → Used / Expired → Soft-Deleted
Only expired or already used tokens may be removed from active use. Valid unused tokens remain usable until ExpirationDate. Cleanup sets IsDeleted = true.

BR-01

ProductVariant is the stock-keeping entity; parent Product must not be used as SKU.

BR-18
Only stable, non-zero IoT weight posts can be attached as verification evidence.
BR-19
Expected weight = unit weight × quantity. The actual IoT weight is accepted
when |actual − expected| ÷ expected ≤ the configured tolerance band (MVP default ±5%). The tolerance value is stored in SystemConfig and may be overridden per ProductCategory.
BR-20
Weight mismatch flags discrepancy and requires manager review before final confirmation if configured.
BR-21
Remote TARE/RESET/CALIBRATE commands are stored as device commands and processed once by the device.
BR-22
Stocktake adjustment requires manager approval and reason code.
BR-23
The counted quantity must be zero or positive.
BR-24
Inbound bottleneck warning compares scheduled inbound workload with storage and labour capacity.
BR-25
Bottleneck warning is advisory and must not block or cancel inbound documents automatically.
BR-26
Bottleneck level is derived from utilization = scheduled inbound load ÷ configured capacity: Normal when utilization < 70%, Warning when 70% ≤ utilization ≤ 90%, Critical when utilization > 90%. Threshold percentages are stored in SystemConfig and configurable per warehouse.
BR-27
Put-away suggestion first applies hard filters (active, non-quarantine,
category allowed, remaining capacity ≥ group quantity), then ranks qualifying
locations by Score = 0.40×CapacityFit + 0.30×OccupancyFit + 0.20×CategoryMatch + 0.10×PriorityNorm (each term normalized 0–1). Ties break by lower Priority number, then lower CurrentOccupancy, then lowest LocationId. The weight set is stored in SystemConfig.
BR-28
The system may return no suggestion when no location has enough capacity.
BR-29
Manual override of put-away suggestion must store selected location, reason and actor.
BR-30
Customer/inbound returns require approval and inspection before stock is changed.
BR-31
Returned goods that fail QC must be routed to a quarantine/non-available location with a reason. Sellable returned goods must be assigned to a valid storage location before final approval. 
BR-32
Return-to-supplier decreases inventory only after final dispatch confirmation.
BR-33
Financial return handling, refunds, credits/accounts payable and carrier pickup automation are out of MVP scope.
BR-34
Inactive ProductVariants and inactive Locations must not be selectable for new warehouse documents or new put-away operations, but they remain visible in historical and audit references. 
BR-35
Finalized inbound, outbound, stocktake, and return documents are read-only. Corrections must be processed through a new authorized adjustment or return process rather than editing the original finalized document. 
BR-36

InventoryTransaction records are append-only and immutable. Each transaction must contain a source reference, ProductVariant, Location, before quantity, after quantity, actor, and timestamp. Corrections are recorded as new transactions. 
BR-37

Stocktake variance equals ActualQuantity minus SystemQuantity. 
BR-38

For each return item, accepted quantity plus damaged quantity must not exceed the inspected or returned quantity. 
BR-39

A Location with on-hand inventory must not be deactivated unless all remaining stock is moved to another active location or an authorized manager records an override reason. 
BR-40 
Users referenced by historical documents, inventory transactions, or audit records must be deactivated or soft-deleted instead of physically deleted. Soft-deleted users cannot log in or receive a valid token, but their historical references remain available for audit. 
BR-41 
StockLite reports are operational and inventory reports only. The system must not present payments, cash flow, financial ledger, refund, credit, or accounts payable data as part of MVP reporting. 
BR-42 
Report exports must use the same active warehouse, date range, status, search, and other filter criteria currently applied on the reporting screen. 
BR-43 
Repeated scans of the same QR code within a defined debounce window must not create duplicate receiving, picking, counting, return inspection, or inventory-changing actions. 
BR-44 
Warehouse Staff may view only activity history generated by their own account. Users with authorized audit or management permissions may view broader activity history according to assigned permissions. 
BR-45 
A date range filter must contain valid dates, and its start date must not be later than its end date. 
BR-46 
Signing out must invalidate the active user session and remove locally stored authentication credentials. Subsequent access to protected functions requires authentication again. 
BR-47 
IoT device availability must be determined from its latest valid heartbeat. When no valid heartbeat is received within the configured timeout, the device must be marked Offline. Offline devices must not receive remote commands until a new valid heartbeat is received. 
BR-48 
Remote IoT commands in Pending status must be marked Expired when their configured expiry time is reached without a valid completion result. Terminal command statuses must not be changed by expiry processing. 
BR-49 
Notification retry processing must resend only retryable notification logs. Successfully delivered or terminal notification logs must not be sent again, and duplicate notification delivery records must not be created. 
BR-50 
Audit retention or archival processing must not modify or delete immutable InventoryTransaction or audit records. It may only mark eligible records using a separate retention or archival status. 
BR-51 
Only expired or revoked UserSession records may be invalidated or removed by session cleanup. Active valid sessions must remain usable. 
BR-52 
Only expired or already used verification tokens may be invalidated or removed by token cleanup. Valid unused tokens must remain usable until their expiry time. 
BR-53
When an approved outbound order is cancelled or its approval is revoked, the
system releases the full remaining QuantityReserved for every line; on-hand is
unchanged.
BR-54
On partial pick or partial shipment confirmation, the system decreases on-hand
and releases reservations only for the confirmed quantity. The unpicked remainder stays reserved until the order is completed or cancelled.
BR-55
Inventory balance updates use optimistic concurrency via a RowVersion token.
When two operations update the same ProductVariant/Location balance concurrently, the stale write is rejected and retried so the system cannot oversell or lose an update; available quantity must never become negative.
