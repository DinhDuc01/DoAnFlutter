1. Overview
1.1 Cost / Time Estimation
The table below lists all deliverable work packages across 6 stages and 14 weeks following the SEP490 project plan template. Total estimated team effort is approximately 380 person-days for 5 members. Based on a working schedule of 6 days per week (Monday through Saturday) and 5 hours per day per team member, each team member is expected to contribute approximately 76 days of work throughout the project, leaving 8 days per member as contingency buffer (approximately 9.5%) for unforeseen risks and additional quality assurance activities.
The formal implementation stage is planned for Weeks 6–11, with a total effort of 220 person-days split across three development iterations. Earlier weeks (1–5) are allocated for planning, high-level design, vertical prototypes, and proof-of-concept (POC) validation—totaling 100 person-days—to reduce implementation risk and ensure technical feasibility before entering the coding phase. The remaining effort (60 person-days) covers verification, validation, user acceptance testing (UAT), and project closure activities in Weeks 12–14

2. Management Approach
2.1 Project Processes
StockLite follows an Iterative & Incremental methodology aligned with FPT SEP490 requirements, incorporating lightweight Scrum ceremonies. The project keeps the standard 14-week planning structure: Week 1 for initiating, Weeks 2–3 for planning, Weeks 4–5 for design, Weeks 6–11 for implementation, Weeks 12–13 for verification and validation, and Week 14 for closing and defense preparation. The implementation stage is organized into three 2-week sprints, each producing a shippable software package.
Development Lifecycle
Defines the chronological phases of the project across the 14-week timeline (Initiating, Planning, Design, Implementation, Verification & Validation, and Closing). It outlines the specific objectives and key deliverables required to transition smoothly from one phase to the next.
Phase
Key Activities
Initiating (Week 1)
Define project charter, identify stakeholders, finalize team roles & responsibilities, submit Report 1.
Planning (Weeks 2–3)
Produce PMP (Report 2), SRS v1.0 (Report 3), vertical code prototypes. Establish GitHub repo, CI/CD pipeline, branching strategy, and communication channels.
Design (Weeks 4–5)
POC to validate architecture decisions (Clean Architecture, QR scan flow, IoT REST API polling). Produce TDS v1.0 (Report 4), Test Plan (Report 5), SRS v1.0.
Implementation (Weeks 6–11)
Three 2-week sprints. Each sprint: Sprint Planning → Daily Standups → Code + Review → Unit Tests → Integration Tests → Sprint Review & Demo → Retrospective → next SRS version.
Verification & Validation (Weeks 12–13)
System testing, UAT with mentor, defect triage & fixes, final software package, user guides.
Closing (Week 14)
Final report, retrospective, project metrics actuals, presentation & defense.

2.2 Quality Management
This section outlines the defensive engineering practices, coding standards, and testing protocols designed to enforce high software quality and prevent architectural decay across all layers of the stack. It sets clear rules for Clean Architecture compliance, mandatory peer code reviews, xUnit backend testing, mobile/web component testing, automated Postman integration collections, and end-to-end system testing scenarios like the core "Receive Goods" workflow.
Quality Activity
Description & Standard
Architecture Compliance
Clean Architecture enforced: Controllers delegate to Services only — no business logic in API layer. Repositories never call SaveChangesAsync(). Services never inject DbContext directly. Violations flagged in code review.
Coding Standards
C# naming conventions (PascalCase methods, camelCase params). XML doc comments on all public Controller and Service methods. No magic strings — use ApiCodeConstants and ErrorMessagesConstants. No hardcoded credentials.
Peer Code Review
All PRs require ≥ 1 approval. Reviewer checklist: architecture compliance, no secrets, naming conventions, Swagger documentation, Serilog logging on error paths.
Unit Testing (Backend)
xUnit tests for Service layer. Mock repositories using Moq. Target: ≥ 70% line coverage on Auth, Product, Inbound/Outbound, Inventory services. Run via GitHub Actions on every push.
Unit Testing (Mobile/Web)
Flutter widget tests for key screens (QR scan, stock take form). Angular component tests via Jasmine/Karma for dashboard and order form components.
Integration Testing
Postman collections per iteration. Tests cover: happy path, validation errors (400), unauthorized (401), not-found (404), and concurrency. Automated in CI/CDI.
System Testing
Receive Goods end-to-end scenario: Inbound created → QR label generated → warehouse staff scans QR by Flutter mobile → system shows expected item and suggested put-away location → IoT scale posts stable weight to backend → system compares expected quantity/weight → staff confirms receiving → system creates InventoryTransaction and updates Inventory → inventory log and audit trail are stored. Executed in Week 11–12.
Static Analysis / Linting
Backend: .editorconfig + Roslyn analyzers. Angular: ESLint + Prettier enforced. Flutter: dart analyze + analysis_options.yaml.
Defect Management
All bugs logged in GitHub Issues with severity, steps to reproduce, and expected vs. actual result. Bugs block the sprint and must be fixed within 24 h. Defect metrics reported in each Test Report.

5.2 Source Code Management
This section governs how the engineering team interacts with the codebase to prevent merge conflicts, preserve branch stability, and maintain a clean development history. It outlines a simplified Git Flow branching strategy with strict rules for main, develop, feature, and bugfix branches, and standardizes commit messages using the Conventional Commits format to ensure every change is clearly documented.
Branching Strategy
This table defines the purpose, operational rules, and naming conventions for each branch within the repository. It enforces branch isolation to prevent configuration conflicts, detailing how code flows from development features up to the production-ready main branch. 
Branch
Purpose & Rules
main
Production-ready code. Protected branch — no direct push allowed. Merged only from develop via approved PR after final regression tests. 
develop
Primary integration branch. All feature and bugfix branches merge here. Must pass CI/CD pipeline before merge. Deployed to staging environment automatically via CI/CD.
feature
Individual feature development. Created from develop. Example: feature/IS-42-product-qr-label. Merged back to develop via PR with ≥ 1 approval.
bugfix
Bug fixes for issues found during testing. Created from develop Example: bugfix/IS-78-inventory-qty-overflow.
